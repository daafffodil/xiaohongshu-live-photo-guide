# 视频转live图排查记录

记录酸汤の视频转实况在小红书离线 H5 小工具中的开发与试错。更新日期为 2026-11-06。本文的版本号属于视频工具，与 shamsham 的版本号分别记录。

已由用户确认可用的是视频工具 1.0.7 和高清版 1.0.8。1.0.14 已在平台发布，但仍有新素材报错；1.0.15 已上传预览，等待用户 iPhone 验证。上线、部署成功和本地测试通过，都不能替代实际素材的手机发布结果。

## 实际流程

```text
选择视频或 GIF
→ 读取和解码
→ 选择片段与居中裁切
→ 生成 JPEG 封面和 H.264 MP4
→ writeTempFile 写入两份临时文件
→ 检查视频可读、尺寸与时长有效
→ postNote 打开原生笔记编辑页
→ 用户编辑并决定是否发布
```

页面里的动态图是素材预览，不能仅凭它在动就认定已经生成了可发布的 live图。这里通过小红书接口把封面与视频配对，没有生成可直接导入 Apple 相册的实况照片文件；Apple Live Photo 的配对元数据方案不能直接替代小工具接口。

## 选择和载入阶段

1.0.1 使用真实的 `<input type="file">` 覆盖可见按钮，让用户的点击直接交给系统选择器。仅通过脚本点击隐藏输入框，在受限容器中可能没有效果。后续把视频和 GIF 合并到同一入口，选择后再核对格式。

1.0.3 的一个确定性代码错误是：打包脚本删除下载按钮，但 `lock()` 仍访问该按钮并设置 `disabled`。异常发生在载入函数的保护范围外，页面停在忙碌状态。修复既包含生成代码，也包含节点空值检查；测试按最终原生 HTML 的真实元素返回结果，不能给已删除控件伪造测试节点。

1.0.4 改为优先让 `<video>` 读取 `URL.createObjectURL(file)`。仅当容器拒绝该路径时，才把文件写入原生存储后读取。媒体元素挂在文档中，主动 `load()`，检查有效首帧、尺寸和时长，失败后释放对象 URL、视频实例并恢复按钮。

这一步成功只证明原素材能读取，不证明重新编码后的发布文件也能写入或发布。

## 发布参数阶段

迁移的是用户确认成功的 shamsham 1.0.7 实际上传包，而不是同项目尚未验证的较新本地实现。具体兼容次序见[主文档](../README.md#shamsham-验证记录)。

从公开契约 `slides_edit + live_photo_sources` 开始。仅错误码为 10001，且明确同时属于 invalid parameter 与 mediaInfo 或 slides resource too few，才继续有限的兼容尝试。取消、编辑页占用、文件不存在和未知失败都不触发参数轮换。没有复制素材凑数量，也不把 live图自动降级成静态图片或视频笔记。

普通视频对照使用：

```js
await sdk.postNote({
  pageType: 'video_publish',
  mediaInfo: {
    video_resources: {
      video_url: media.video_url,
      cover_url: media.url
    }
  }
});
```

两个入口共用同一组已准备的临时路径，才能有效比较文件交接与媒体参数问题。发布页可能持续打开很久，不给 `postNote` 加短超时后自动解锁重发；超时保护用于素材读取、编码和写入。

## 文件找不到与成功修复

用户在 1.0.6 中确认绿色 Demo 可发布，但上传约两秒 MP4 和拍摄视频均返回 `postNote:fail file not found`。

代码按生成文件的 4 MiB 阈值分流：小文件用 `writeTempFile` 返回路径，大文件分片写入持久工作区后构造路径。Demo 输出 2,050,451 字节，复杂两秒测试素材输出 4,744,112 字节，后者能够在本地解码，却走了另一条文件交接路径。

1.0.7 取消发布产物的大小分流，封面与 MP4 均通过 `writeTempFile`，只使用返回的完整 `filePath`。两次写入和视频校验全部成功后才调用 `postNote`。文件不存在时清除缓存，下次用户主动点击才重新生成，不自动重复发布。

用户随后扫码确认 1.0.7 可用，这是本案例真正的手机成功反馈。现有证据支持文件交接分支是关键修复点，但没有原生文件系统日志，不能推出所有持久路径在所有客户端都不支持。4 MiB 也是旧代码阈值，不是已知的小红书硬限制。

## 高清版的成功与限制

1.0.7 固定输出 384×512，且曾把 Demo GIF 缩到 160×212。这解释了发布成功但画面模糊的另一类问题。

1.0.8 按素材居中裁切后的有效像素输出，最高 1080×1440，不放大小素材。生成时切换 Canvas 的实际像素尺寸，封面与视频同尺寸，结束或异常后恢复预览画布。去掉 Demo 的低清缩图步骤；发布桥接与入口保持和成功的 1.0.7 一致。

用户随后明确确认该版手机发布没有问题。[1.0.8 完整原始包](../snapshots/酸汤の视频转实况-1.0.8.zip)及校验值已归档。此结论覆盖当时测试的素材，不表示任意运动复杂度、大小或设备都已验证。

## 存储配额与单次请求大小

这两类报错必须分开处理。

| 报错 | 所处阶段与含义 | 本项目处理 |
| --- | --- | --- |
| writeFile:fail storage quota exceeded; reason=total_over_limit | 用户选择 11 秒素材后，原生读取回退写入工作区失败，尚未进入生成和发布 | 1.0.14 的 MP4 读取回退改用临时文件；MOV 保留分片，先查可用容量，失败仅删除本次创建的部分文件 |
| 10004 writeTempFile:fail payload invalid; reason=payload too large | 用户在 iPhone 上约一秒素材已载入，点击生成后写入发布素材失败，还未调用 postNote | 1.0.15 先压缩编码并检查输出体积，明确超大时才降低码率有限重试 |

没有用户原始视频与完整设备日志，不能仅用“11 秒”断言源文件大小，也不能把后一条错误说成 live图发布器拒绝了参数。时长、像素尺寸、帧数、运动内容和编码方式都会影响体积。

既有离线 H.264 编码器对变化宏块使用 I_PCM，未变化块可跳过。静态或局部变化 Demo 的结果不能代表普通运动视频；提高分辨率后，即使只有一秒也可能生成很大的 MP4。Base64 还会增加约三分之一的传输体积。

截至本轮核对，官方公开 writeTempFile 文档没有给出足以据此确定本案例上限的数值。不要把 4 MiB 旧分支或下面的项目预算写成官方限制，也不要通过反复写入同一个超大请求尝试解决。

## 1.0.15 预览方案

新增能力检测后的 WebCodecs AVC 压缩，使用编码器提供的 AVCDecoderConfigurationRecord 封装 MP4，保留裁切后的分辨率和所选时长。默认目标码率 4 Mbps，应用自己的输出预算为 2,500,000 字节，为 Base64 膨胀留出余量。

只有明确的 payload too large 或应用预算超限，才以 1.5 Mbps 再编码一次。重试发生在打开发布页之前。已知超大的封面或视频不继续传给写入接口；不通过回到此前失败的持久路径或缩小分辨率绕开问题。

`VideoEncoder`、`VideoFrame` 和 AVC 配置均须实际检测。容器或内核不支持时，小素材可使用既有软件编码，大素材会提示当前环境不支持压缩。不能因为普通浏览器支持，就承诺 iPhone 小红书容器一定可用。没有缺帧或缺编码配置的情况下才输出文件，并释放编码器和帧资源。

超过三秒的素材显示缩略图选择条，黄色选框固定三秒，可左右拖动或点按。选择变更同时影响预览、封面和 MP4，并清除旧发布缓存。三秒以内使用完整时长。重新选择素材重置起点，切换比例保留起点，生成中禁用修改。

本地验证结果：

| 测试 | 结果 |
| --- | --- |
| 自动检查 | 50 项通过，覆盖选择区间、缓存、重试、超大写入阻止、缺帧和编码资源清理 |
| 一秒运动测试视频 | 1080×1440，526,292 字节，可播放 |
| 11 秒素材选择 6.15 秒起点 | 导出三秒，1080×1440，36 帧，1,979,301 字节，可播放且 FFmpeg 完整解码通过 |
| 导出首帧核对 | 最近匹配源文件 6.125 秒帧，符合源素材 24fps 的帧时间，未回到开头 |
| 9:16 | 一秒，1080×1920，可播放 |
| 末尾选择 | 11 秒素材可选 8.0–11.0 秒 |
| 短屏布局 | 320×568 下选择条和发布区无横向溢出，页面高度 568 |

预览上传包为 1,587,795 字节，SHA256 为 `7d7aa743bdb668e363d4bb2356b2373ac9fc624a03187abeaeb95c614c837363`，12 文件审计零警告。2026-11-06 创服显示部署成功，只获取预览二维码，未提交审核。上述本地结果不等于小红书原生发布成功；本版不列入成功版本归档，等待用户 iPhone 验证，Android 也未验证。

## 后续验证

使用同一个 1.0.15 预览包，记录手机系统、小红书客户端版本与具体素材：先复测此前报错的一秒视频，再用长视频选择中间与末尾三秒。分别确认预览区间、生成文件、原生编辑页里的动态效果，以及直接发布视频的对照结果。

不要把进入编辑页、接口回调返回、笔记发出或笔记审核通过混为一项成功。验证通过后追加原始包与校验值，保持已成功版本不变。
